# CLAUDE.md — LRob - Gutenberg Blur

WordPress plugin adding `backdrop-filter` blur + a customizable "glass" effect to
core blocks (Group, Columns, Column, Row, Cover) via Gutenberg block attributes.

## Layout

- `lrob-gutenberg-blur.php` — main file: singleton bootstrap, editor enqueue,
  the `render_block` frontend filter, hex→rgb + inline-style generation.
- `includes/class-lrob-blur-updater.php` — self-hosted GitHub updater.
- `assets/`
  - `style.css` — the ONLY frontend CSS. Holds the `.lrob-blur` rule with
    `backdrop-filter`. Used by both editor and frontend.
  - `common.js` — shared JS utils (clamp, hexToRgb, supported-block list).
  - `editor-attributes.js` — registers the `lrob*` block attributes.
  - `editor-inspector.js` — sidebar controls.
  - `editor-preview.js` — live editor preview (mirrors the PHP output).
  - `editor-save.js` — writes inline styles into saved block markup.
  - `editor.js` — LEGACY monolith, no longer enqueued. Don't edit; it's dead.
- `languages/` — i18n. `.po`/`.pot` are source; `.mo`/`.json` are generated by `release.sh`.

The effect is driven by inline styles + CSS custom properties (`--lrob-blur`,
`--lrob-saturation`, `--lrob-bg-color`). Three code paths must stay in sync when
the styling logic changes — they reimplement the same math:
1. PHP `render_block_filter()` (frontend),
2. `editor-preview.js` (editor canvas),
3. `editor-save.js` (saved HTML).

## Frontend CSS delivery — do NOT make this conditional on post_content

The frontend stylesheet is printed inline, once per request, from
`render_block_filter()` via `maybe_inline_css()` (guarded by the static
`$inline_css_printed`). It is intentionally **not** `wp_enqueue_style`'d.

Why: a blur block can live in an FSE template or template part (site header,
footer, the "Pages" template…). Those are NOT in `$post->post_content` and they
render *after* `wp_head()`. The old `enqueue_frontend_assets()` gated the
stylesheet on scanning `$post->post_content`, so blocks inside templates never
loaded `style.css` → the `backdrop-filter` rule was absent → the glass frame
(inline box-shadow/color) showed but there was **no blur**. This was the 1.0.2 bug.

`render_block` fires for every block wherever it lives, so emitting the CSS from
there covers post content, template parts, patterns, widgets — with no extra HTTP
request. If you ever "optimize" this back into a conditional enqueue, you will
reintroduce the bug.

## Editor CSS must load into the iframed canvas

`style.css` is enqueued for the editor via `enqueue_canvas_style()` on the
**`enqueue_block_assets`** hook (admin-gated), NOT `enqueue_block_editor_assets`.
Since WP 6.x the editor canvas is an iframe; `enqueue_block_editor_assets` only
reaches the editor's outer document, so `backdrop-filter` (in `style.css`) was
absent in the canvas — a Glass block rendered its inline frame/shadow (from
`editor-preview.js`) but no blur. `enqueue_block_assets` reaches the canvas.
The block-registration JS stays on `enqueue_block_editor_assets` (it must run in
the outer frame). Don't move the stylesheet back, or the editor preview breaks
again (this was the 1.0.3 fix).

## Auto-update (GitHub Releases)

`LRob_Blur_Updater` hooks `pre_set_site_transient_update_plugins` and
`plugins_api` to make WordPress update the plugin from this repo's GitHub
Releases. It reads `releases/latest`, compares `tag_name` (vX.Y.Z, the `v` is
stripped) against `LROB_BLUR_VERSION`, caches the API response in a transient
(`lrob_blur_gh_release`, 1h; `'none'` sentinel on failure), and force-refreshes on
`update-core.php` or `?force-check=1`.

Hard requirement: each release MUST attach an asset named
`lrob-gutenberg-blur-X.Y.Z.zip` whose archive has a single top-level folder
`lrob-gutenberg-blur/`. The updater deliberately ignores GitHub's auto-generated
source tarball (its folder is the commit hash → would install side-by-side
instead of replacing). `release.sh` produces a correctly-structured zip.

Adapted from the LRob - Email Toolkit updater (`../lrob-email-toolkit`).

## Release process

1. Bump the version in **two** places in `lrob-gutenberg-blur.php`: the header
   `Version:` line AND `define('LROB_BLUR_VERSION', ...)`. Keep them identical.
2. Update the README `## Changelog` section (ascending order).
3. `./release.sh` — regenerates translations and builds
   `../releases/lrob-gutenberg-blur-<version>.zip` (the `releases/` dir is the
   sibling folder, outside this repo). Needs php-cli, wp-cli, gettext, zip.
4. Commit + push to `main`.
5. Publish the GitHub release with the zip attached, e.g.:
   `gh release create vX.Y.Z ../releases/lrob-gutenberg-blur-X.Y.Z.zip --target main --title "..." --notes-file <notes>`
6. Release notes are for END USERS: focus on what changed for them, not internals
   or where code came from.

Installs already on a version without the updater (≤1.0.1) won't auto-update to
the first updater-bearing release — that one is installed manually; auto-update
takes over from the next version on.

## Visual testing

There's no browser in CI, but blur is visual. A headless Chromium is available at
`/usr/lib64/chromium-browser/headless_shell` — render a small HTML harness
(replicate the block + `style.css`, a Cover with an image behind) and
`--screenshot` to confirm `backdrop-filter` actually shows. Remember
`backdrop-filter` only looks like "blur" when there's non-uniform content behind
the element and the element's own background isn't too opaque.

## Conventions

- PHP: tabs/4-space style as in the existing file, `array()` long syntax, classes
  prefixed `LRob_`/`LROB_`. Guard files with `if (!defined('ABSPATH')) exit;`.
- Supported blocks list lives in two spots: PHP `$supported_blocks` and JS
  `window.LRobBlur.allowedBlocks`. Update both.
